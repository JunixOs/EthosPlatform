BUGS REPORTADOS EN LA TAREA — ESTADO REAL VERIFICADO
============================================================

BUG (reportado) 1: Favoritos devuelve URL duplicada /api/api/
Estado: NO REPRODUCIDO.
Archivo: apps/frontend/src/presentacion/features/favoritos/services/favoritos.service.ts
El servicio usa el cliente `api` compartido con rutas relativas
(`/favoritos/${id}`, `/favoritos/mios`) sin prefijo duplicado. El flujo de
favoritos end-to-end (dar favorito, ver en "Mis favoritos", quitarlo) pasa
correctamente en flujo-favoritos.spec.ts.

BUG (reportado) 2: Etiquetas no se asocian correctamente
Estado: REAL, pero la causa no era el backend sino el frontend + tests desactualizados.
- El backend (AsociarEtiquetasUseCase y la tabla experiencia_etiqueta) funciona
  bien: verificado insertando etiquetas reales vía UI y confirmando que
  aparecen en el detalle de la experiencia.
- El bug real: el formulario de creación (CreateExperienciaPage.tsx) y edición
  (EditExperienciaPage.tsx) NO asocian etiquetas — ese flujo vive únicamente
  en la sección "Editar etiquetas" del detalle de la experiencia
  (EditarEtiquetasSection.tsx), que sí existía pero no estaba probada
  correctamente. Ver fix #1 y #3 abajo.

BUG (reportado) 3: Admin devuelve 401 en lugar de 403
Estado: NO REPRODUCIDO.
Archivo: apps/backend/src/logica/interface_adapters/middleware/authMiddleware.ts
`requireAdmin()` ya lanza `ForbiddenException` (403) cuando `req.user.rol !== 'admin'`.
El 401 solo se devuelve cuando falta o es inválido el token (comportamiento correcto).

BUG (reportado) 4: Logout no invalida el token
Estado: NO REPRODUCIDO.
El middleware de auth ya verifica contra `ISesionRepository.findByToken()` y
rechaza con `TokenRevokedException` si la sesión fue eliminada (logout) o no
es válida. Es decir, el JWT por sí solo no basta: se valida la sesión en BD
en cada request.

============================================================
BUGS ENCONTRADOS Y REPARADOS EN ESTA SESIÓN
============================================================

Fix #1 — Labels sin asociación programática en formularios de experiencia
Archivos:
  - apps/frontend/src/presentacion/features/experiencias/pages/CreateExperienciaPage.tsx
  - apps/frontend/src/presentacion/features/experiencias/pages/EditExperienciaPage.tsx
Síntoma: los `<label>` de Título, Descripción, "¿Qué dice la moral?" y "¿Qué
dice tu ética?" no tenían `htmlFor`/`id`, por lo que cualquier lector de
pantalla o test con `getByLabel(...)` no podía ubicar el campo (fallaba con
timeout). Esto bloqueaba por completo la creación/edición de experiencias
en los tests E2E (flujo-experiencias, flujo-etiquetas).
Fix: se agregó `id` a cada input/textarea y `htmlFor` a su `<label>`
correspondiente en ambos formularios.
Impacto real: además de arreglar los tests, es un bug de accesibilidad
genuino en producción.

Fix #2 — Selector ambiguo en test de reportes
Archivo: tests/e2e/specs/flujo-reportes.spec.ts
Síntoma: `getByRole('button', { name: /reportar/i })` matcheaba dos botones
a la vez (el link que abre el modal y el submit dentro del modal), causando
"strict mode violation".
Fix: se usa `.last()` para apuntar al botón de submit dentro del modal,
igual que ya se hacía con `.first()` para el trigger.
Nota: bug de test, no de la app — el componente ReportarModal funciona bien.

Fix #3 — flujo-etiquetas.spec.ts asumía un flujo que no existe
Archivo: tests/e2e/specs/flujo-etiquetas.spec.ts
Síntoma: el test intentaba agregar etiquetas y publicar directamente desde
el formulario de creación (input de etiquetas + botón "Publicar"), pero ese
input no existe ahí — las etiquetas se agregan desde el detalle de la
experiencia vía `EditarEtiquetasSection`.
Fix: se reescribió el test para reflejar el flujo real: crear como borrador
→ ir al detalle → agregar etiquetas con el input "Escribe y presiona
Enter..." → click en "Guardar etiquetas" → verificar que aparecen `#etica`
y `#moral`.

Fix #4 — Falsos positivos cruzados entre proyectos de Playwright
Archivo: tests/e2e/playwright.config.ts
Síntoma: los proyectos `chromium-auth` y `chromium-admin` filtraban tests
con un `grep` por palabras clave (`/auth|favoritos|.../` y `/admin/`) sobre
el título completo de cada test. Como varios tests de `components.spec.ts`
usan como *nombre de test* una ruta (p. ej. "/admin/usuarios redirige a
/login" o "/favoritos redirige a /login"), esos tests de "sin sesión"
terminaban ejecutándose también bajo una sesión ya autenticada — y fallaban
porque el comportamiento esperado (mostrar botón "Iniciar sesión", redirigir
a /login, etc.) no aplica si ya hay sesión. Esto generaba ~24 fallos
espurios en cada corrida completa que no tenían nada que ver con bugs reales.
Fix: se reemplazó el `grep` por keyword con `testMatch`/`testIgnore` basado
en nombre de archivo (los specs `flujo-*.spec.ts` que requieren sesión), lo
que elimina la ambigüedad por coincidencia de substring.

============================================================
NOTAS / NO SON BUGS DE CÓDIGO
============================================================

- Test flaky ocasional en flujo-auth.spec.ts ("logout elimina sesión y
  redirige"): en dos corridas completas anteriores falló 1/2 veces por un
  timeout de 5s justo después de login, pero pasó en el retry y en corridas
  posteriores aisladas. Parece jitter de timing en Windows bajo carga, no
  un bug reproducible del login. Si vuelve a aparecer con frecuencia, vale
  la pena revisar el tiempo de respuesta del endpoint de login bajo carga
  concurrente de tests.
- Los navegadores Firefox y WebKit de Playwright no están instalados en
  esta máquina (`pnpm exec playwright install` pendiente), por lo que todos
  los tests bajo esos proyectos fallan con "Executable doesn't exist". Es
  un tema de entorno local, no del código. Los smoke tests se validaron
  con Chromium (chromium / chromium-auth / chromium-admin), que cubre los
  flujos funcionales pedidos.
